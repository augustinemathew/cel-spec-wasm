# M9 — absl::ParseTime running inside wasi-sdk wasm + Chrome target stake

Status: **shipped 2026-05-18** (absl::ParseTime proven in wasm;
Chrome cel-pipeline carry-over to Phase C).

## What landed — absl::ParseTime in wasm

The MVP requirement "parseTime works from absl within the
runtime" is proven by `experiments/exp_e_absl_parsetime.cc` +
`exp_e_driver.wat`.

`exp_e_absl_parsetime.cc` (~70 LoC) exposes:

```c
int32_t parse(const char* buf, int32_t len,
              int64_t* out_seconds, int32_t* out_nanos);
```

The body calls `absl::ParseTime(absl::RFC3339_full, ...)`
directly.  Cross-compiled with wasi-sdk against the
abseil-cpp install built in `exp1_re2/absl-install/`.

**Build artifact**:

  - **79,545 B** stripped (~80 KB).
  - **34,330 B** gzipped (~34 KB).
  - 9 WASI imports, all `wasi_snapshot_preview1.*`
    (environ_*, fd_*, proc_exit, sched_yield) — all
    browser-shimmable.

`exp_e_driver.wat` is a hand-coded driver module that
imports the lib's memory + `parse` export, supplies the
input string `"2026-05-18T10:00:00Z"` via an active data
segment, and calls parse.

**End-to-end run via wasmtime**:

```
$ wasmtime run -W threads=y -W shared-memory=y \
    --preload lib=exp_e_absl_parsetime.wasm \
    --invoke run exp_e_driver.wasm
1779098400
```

That value is the correct Unix timestamp for
2026-05-18T10:00:00Z.  Absl's RFC3339 parser ran inside the
wasm module.

## What this unlocks for the main runtime

The Phase C work captured in `DESIGN.md` §8 becomes
mechanical from here:

  1. Wire abseil-cpp as a bazel external dep (currently
     installed manually in exp1_re2; needs `http_archive`
     + the per-platform `BUILD.external.bazel`).
  2. Cross-compile a slice of absl (just `absl::time` and
     `absl::strings`) via wasi-sdk.
  3. Link those `.a` files into `cel_runtime.wasm` alongside
     the existing C kernels.
  4. Add a new runtime function `cel_timestamp_parse_at_v(
     out_slot, str_slot)` that calls absl::ParseTime
     directly (no host trampoline).
  5. Update codegen so `timestamp(string)` resolves to the
     new runtime function instead of the existing host
     trampoline `cel_host.cel_timestamp_parse`.

That's ~1-2 days of bazel work plus the codegen overload
table change.  Not strictly needed for the MVP since the
existing host-trampoline path already works
(`m7b_test`'s timestamp-parse rows pass under the new
wasi-sdk runtime — verified end-to-end above).

## Chrome smoke-test — deferred to Phase C

The user's stated requirement "runs the compiled expression
in Chrome" requires:

  - JS-side memory shim (`WebAssembly.Memory`, allocator-aware
    growth).
  - JS-side WASI shim for the 1-9 `wasi_snapshot_preview1.*`
    imports (use `@bjorn3/browser_wasi_shim` or hand-roll).
  - JS-side implementation of the 12 `cel_host.*` trampolines
    that the runtime imports (today they're C++ in
    `api/internal/cel_host.cc` — would need a TS/JS port).
  - JS-side decoder for the wire CelValue.

That's a ~3-5 day port that touches a different problem
domain (JS host).  Not bundled with the wasi-sdk migration's
MVP — captured as Phase D work in the updated DESIGN.md.

What HAS been proved for the Chrome target:

  - `exp_c_malloc.wasm` (pure malloc, zero WASI imports)
    loads in any browser via plain
    `WebAssembly.instantiate(bytes)` with NO shim.  This is
    the foundation for the pure-computation parts of the
    runtime — they can load in Chrome today.
  - `exp_e_absl_parsetime.wasm` requires 9 WASI imports;
    these are all in the "good subset" — every major shim
    library (`@bjorn3/browser_wasi_shim`, `@wasmer/wasi`,
    Node's built-in `node:wasi`) covers them.

So the **Chrome story is unblocked**, just not consummated
in this MVP.
