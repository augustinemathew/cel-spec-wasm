## What landed

  - `MODULE.bazel`: 4 `http_archive` blocks for wasi-sdk-25:
    - `wasi_sdk_darwin_arm64` (sha 256: `e1e529ea...`)
    - `wasi_sdk_darwin_x86_64` (sha 256: `55e3ff3f...`)
    - `wasi_sdk_linux_arm64` (sha 256: `47fccad8...`)
    - `wasi_sdk_linux_x86_64` (sha 256: `52640dde...`)
    All four pinned with verified sha256 (we curled each
    100 MB tarball and computed locally; GitHub does not
    publish `.sha256` files alongside the release assets).
  - `third_party/wasi_sdk/BUILD.external.bazel` (NEW): the
    BUILD file injected into each per-platform repo.
    Exposes `clang`, `clang++`, `ar`, `ranlib`, `sysroot`
    as filegroups.
  - `third_party/wasi_sdk/BUILD.bazel` (NEW): top-level
    aliases (`//third_party/wasi_sdk:clang`, etc.) that
    point at the darwin-arm64 variant today.

## Plan-vs-execution deltas

  - **Cross-platform select isn't wired yet.**  The first
    attempt used `select({ "@platforms//os:macos": ..., })`
    nested selects on top of `@platforms//cpu:arm64`/`x86_64`.
    Two issues: (a) `@platforms` isn't a declared bazel_dep
    in this MODULE.bazel; (b) `alias.actual` doesn't accept
    nested `select`s, only flat ones with `selects.config_setting_group`
    from bazel_skylib.

    For M1's acceptance gate (build works on the dev box),
    a flat alias to the darwin-arm64 variant suffices.  Adding
    `@platforms` as a dep + a `selects.config_setting_group`
    per `(os, cpu)` combination is a follow-up when CI extends
    beyond macOS.  Tracked in M1.1 below.

  - **Tarball cache hit.**  The dev box already had the
    darwin-arm64 wasi-sdk extracted at
    `wasm_compilation_experiments/exp1_re2/wasi-sdk-25.0-arm64-macos/`
    from the prior experiments.  Bazel's repository rule
    re-downloaded into its own cache (the canonical wasi-sdk
    location is now `external/_main~_repo_rules~wasi_sdk_darwin_arm64`);
    the symlinked one in the experiments dir is unchanged.
