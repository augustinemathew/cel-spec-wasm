# m28 Prototype Review — 2026-06-08

## Summary

**Verdict: mixed.** The prototype lands the core architectural shape from
`m28-configurable-linking.md` — `LinkMode::kStatic` end-to-end through
Compile → Plan → Eval, with 51/51 e2e passing in both modes — and surfaces
four load-bearing invariants the design doc never anticipated. Each of those
invariants was paid for in debugging time; none is currently pinned by a
focused regression test, and one (no-merge-similar-functions in the strip
tool) is wholly unguarded — a future Binaryen-pass refactor that adds the
catch-all `BinaryenModuleOptimize` back will silently regress static-mode
codegen with no test signal. Additionally, two design-doc commitments were
quietly dropped or deferred: `__wasm_call_ctors` is never invoked (design
§5.4 promised it), and the rodata-budget invariant against
`CELWASM_RESERVED_LOW_MEMORY_BYTES` (8 KiB) has no assertion.

**Top 3 to look at first:**

1. **§2 invariant #1 — Strip tool's pass list is load-bearing.** The
   one-line `BinaryenModuleRunPasses({"remove-unused-module-elements"})`
   call replaces `BinaryenModuleOptimize`. No test currently asserts the
   resulting module preserves distinct exports for semantically-identical
   functions (e.g. `cel_dur_to_int_at_v` vs `cel_dur_seconds_at_v`).
2. **§4 P1 — `__wasm_call_ctors` is silently skipped in static mode.**
   Tested expressions don't reach cctz init paths so all 51 e2e pass; the
   moment a static-mode Program touches `timestamp(...)` / `duration(...)`
   / regex / format paths that rely on global C++ ctors, behaviour is
   undefined. Design §5.4 explicitly said `CallInit` would invoke
   `_initialize` or `__wasm_call_ctors`. Test `m28_static_link_test.cc`
   even *names* this gap ("the missing `__wasm_call_ctors`... doesn't
   surface here").
3. **§3 design drift — the proposed `HasCelImports(bytes)` dispatch.** The
   prototype implements this exactly as designed but plumbs link-mode
   detection through a hand-rolled wasm-binary walker in `eval/engine.cc`
   rather than reading the explicit `cel.abi` `LinkMode` field that the
   design's §6 reserved. The proto field was deferred to Phase 3, so today
   the implicit detection is the *only* signal — a Program with no `cel.*`
   imports for any unrelated reason would be misclassified.

## 2. Invariants the prototype implicitly enforces

This is the keystone section. Each invariant below is now load-bearing in
production but was either undocumented in the design or surfaced during
debugging. Every one needs an explicit assertion or a focused regression
test before m28 closes; today most are guarded only by the absence of
visible failure in the 51 e2e cases.

### Invariant 1 — Strip tool MUST NOT run `merge-similar-functions` / inliners

- **Where enforced:** `runtime/strip_command_wrappers.cc:132` —
  `BinaryenModuleRunPasses({"remove-unused-module-elements"})` only.
- **What breaks if regressed:** codegen calls runtime helpers by name
  (`BinaryenCall("cel_dur_to_int_at_v", …)`). `BinaryenModuleOptimize`
  collapses functions with identical bodies (e.g. `cel_dur_to_int_at_v` and
  `cel_dur_seconds_at_v`, both `local.get 0; i64.load; → i32`) and
  retargets the dead twin's export to the survivor. Static-mode codegen
  then fails to resolve `BinaryenCall("cel_dur_to_int_at_v")` because the
  function with that internal name is gone. Failure surfaces at Compile
  time as a Binaryen validation error or — worse, depending on Binaryen
  version — silently emits a call to the wrong helper.
- **Loud or silent?** Today, **silent** in test coverage. The existing
  `cel_runtime_stripped_wasm_bytes_test` only checks:
  (a) wasm magic, (b) no `.command_export` suffix, (c) artifact strictly
  smaller. None of these would catch a merge regression. A future
  contributor "cleaning up" the strip tool by reverting to
  `BinaryenModuleOptimize` (the natural shape) would not see a red test.
- **Missing test:** "stripped runtime contains every codegen-targeted
  helper as a distinct function." Should iterate the catalogue (`abi/
  runtime_catalogue`) and assert each name maps to a distinct Binaryen
  function id.

### Invariant 2 — Codegen `BinaryenLoad`/`BinaryenStore` MUST pass `nullptr` for memory name

- **Where enforced:** 11 sites — 2 in `expr_lower.cc` (`LoadSlotI32Eq`,
  `LoadSlotI32Ne`), 9 in `expr_lower_comprehension.cc`
  (`LoadAccuBoolPayload`, `EmitListPrologue`, `EmitLoadSourceCount`,
  `EmitWriteIntCelValueToSlot`).
- **What breaks if regressed:** the adopted runtime declares its memory
  with internal name `"0"` (wasi-libc / wasm-ld convention), our
  freshly-built dynamic-mode modules use `"memory"`. A hardcoded
  `"memory"` in `BinaryenLoad` then crashes Binaryen's serializer in
  `kStatic` mode because it can't resolve a memory by that name. Symptom
  in the prototype was a hard crash during ternary lowering.
- **Loud or silent?** Loud in dynamic mode (works fine, since dynamic
  builds a memory named `"memory"`) and **loud in static mode** —
  serializer aborts. But the inverse regression — someone re-adds
  `"memory"` to a new `BinaryenLoad` call site in some future codegen arm
  — is **silent** in dynamic-only test runs and fires only when static
  mode exercises that arm. Today no test pins all 11 sites; nothing in
  CI flags a new `BinaryenLoad(..., "memory")` introduction.
- **Missing test:** a lint or codegen test that walks the emitted module
  in static mode for an expression matrix exercising each codegen arm
  (kSelect, comprehension prologue, accu loads, EmitWriteInt) — the
  parametric e2e covers some but not the full surface (no kComprehension,
  no kSelect-on-proto in static mode).
- **Better fix:** consider hiding the memory-name arg behind a codegen
  helper that always passes `nullptr`, and grepping for raw
  `BinaryenLoad(` / `BinaryenStore(` calls in lint (§7 candidate).

### Invariant 3 — Codegen-canonical `cel_host.*` import names MUST be installed in BOTH link modes

- **Where enforced:** `compiler/internal/compile.cc::InstallCelHostImports`
  is now called from BOTH `Compile()` (dynamic) and `CompileStatic`. The
  adopted runtime module also declares its own `cel_host.*` imports under
  wasm-ld-assigned internal names (`$cel_host_cel_get_field` etc.) — so a
  static-mode Program has **two** parallel imports of the same `(cel_host,
  cel_get_field, …)` triple.
- **What breaks if regressed:** if `InstallCelHostImports` is skipped in
  `CompileStatic`, expr-side `BinaryenCall(kCelHostGetFieldInternalName)`
  resolves to no function — Binaryen validation fails. The "obvious"
  cleanup ("we already have these imports from the adopted module, why
  install duplicates?") regresses static-mode codegen.
- **Loud or silent?** Loud at compile time (Binaryen validation fires).
  The shape itself is awkward — wasm spec permits multiple imports under
  the same `(module, base, type)` triple, but it's an unusual pattern.
- **Possible refactor:** Either rename the adopted runtime's `cel_host.*`
  imports to the codegen-canonical names at strip time (preferred — one
  set of imports), or document the dual-imports invariant explicitly in
  the strip tool and the static-mode compile path. Today both sides have
  comments; an automated assertion ("module has exactly N `cel_host.*`
  imports, where N is the catalogue count or 2N for the dual case") is
  absent.

### Invariant 4 — Strip tool MUST call `BinaryenSetDebugInfo(1)` before write

- **Where enforced:** `runtime/strip_command_wrappers.cc:88` — process-
  global setter, before any pass runs and before the write.
- **What breaks if regressed:** Binaryen drops the wasm `name` custom
  section on write unless this is on. Without function names, the
  compiler's intra-module `BinaryenCall("arena_reset", …)` etc. cannot
  resolve in static mode (functions become anonymous `$<index>`-named).
  Static-mode `Compile()` fails with "function not found" inside the
  adopted module.
- **Loud or silent?** Loud (Compile errors). But the call is a *process-
  global* side-effect — `BinaryenSetDebugInfo(1)` affects all Binaryen
  modules in the process from that point on, not just `m`. If a future
  refactor moves the strip tool into a library and another Binaryen
  caller in the same process sets `BinaryenSetDebugInfo(0)`, the strip
  tool silently regresses on next invocation. Currently safe only because
  `strip_command_wrappers` is a standalone `cc_binary`.
- **Missing test:** stripped-bytes test should walk function indices and
  assert at least N (catalogue size) are *named*, not anonymous.

### Invariant 5 — Adopted module's feature set is the UNION of declared + DefaultFeatures

- **Where enforced:** `compiler/codegen/module.cc::Adopt` — sets features
  to `BinaryenModuleGetFeatures(out.module_) | DefaultFeatures()`.
- **What breaks if regressed:** narrowing the adopted module's feature set
  trips Binaryen's internal assertion that feature dependencies
  (e.g. `BulkMemoryOpt` implies `BulkMemory`) are consistent. The runtime
  is built with clang flags that turn on more than our default set —
  preserving them is mandatory.
- **Loud or silent?** Loud (Binaryen ABSL_CHECK / abort), but only at
  Compile time. Comment in the code captures the rationale; no test pins
  it.

### Invariant 6 — Reserved low-memory region: expr rodata MUST fit in `[0, CELWASM_RESERVED_LOW_MEMORY_BYTES)`

- **Where enforced (asymmetric):** dynamic mode — expr module's data
  segment goes into its own fresh memory at offset `layout.rodata_base`,
  no collision possible. Static mode — the runtime's memory is built with
  `-Wl,--global-base=8192`; the bottom 8 KiB is reserved by design. The
  `CompileStatic` comment cites this but **nothing asserts**
  `layout.rodata_base + layout.rodata.size() <=
  CELWASM_RESERVED_LOW_MEMORY_BYTES`.
- **What breaks if regressed:** rodata silently overwrites the runtime's
  static .data section (cctz arrays, string tables, …). No trap, no
  validation error — corruption, then unexplained wrong answers at Eval.
- **Loud or silent?** **Silent.** This is a corruption candidate. A
  large string literal in an expression (the m28 doc itself flags
  "N=10000 string literal rodata budget" as a separate concern in §10)
  would silently corrupt the runtime.
- **Missing test + fix:** `CompileStatic` should return
  `ResourceExhaustedError` if rodata doesn't fit; an explicit
  `ABSL_CHECK` on `layout.rodata_base + layout.rodata.size() <=
  CELWASM_RESERVED_LOW_MEMORY_BYTES` is the minimum bar.

### Invariant 7 — `helpers_instance` MUST be the runtime helpers source at every reader

- **Where enforced:** `eval/internal/instance_impl.h::helpers_instance`,
  set in two places — `InstantiateRuntime` (dynamic) and `Engine::Plan`'s
  `if (is_static)` arm (static). 6 reader sites: `BindRuntimeMemory`,
  `BindAllRuntimeExports`, `BindRuntimeFuncHandles` (×2 — arena_alloc and
  malloc), `SeedRuntimeArena`, `EnforceRuntimeMemoryInvariants`.
- **What breaks if regressed:** any single reader still reading the old
  field (or a stale handle) reads from wasmtime's zero-initialised
  `wasmtime_instance_t{}` and trips "instance has no export" at first
  lookup. The full rename across `engine.cc` looks complete (grep
  confirms zero non-doc references to `runtime_instance` in
  `eval/`/`compiler/`); one stale reference remains in
  `eval/engine_test.cc:187` (in a comment only — not a regression risk
  but flagged in §6).
- **Loud or silent?** Loud (FailedPrecondition).

### Invariant 8 — `is_static` detection is a wasm-binary section walk over Program bytes

- **Where enforced:** `eval/engine.cc::HasCelImports` — ~85 lines of
  hand-rolled ULEB128 + section walker that scans for any import with
  module string `"cel"`.
- **What breaks if regressed:** misclassification routes through the
  wrong Plan branch. Static program seen as dynamic → tries to
  instantiate runtime separately, fails to bind memory, traps on Eval
  with a confusing error. Dynamic program seen as static → expr_instance
  becomes both itself and helpers_instance, but expr lacks `arena_init` /
  `arena_alloc` exports — first `wasmtime_instance_export_get` returns
  false, FailedPrecondition. Loud either way.
- **Subtler regression:** A *future* link mode (component-model-static,
  hybrid) that genuinely has no `cel.*` imports but isn't fully static
  would be misclassified. The design's §6.3 reserved an `enum LinkMode`
  in `cel.abi` precisely for this; the prototype implements the implicit-
  detection arm only.
- **Coverage:** no unit test for `HasCelImports` itself. Truncated /
  malformed wasm returns false (safe-ish), but no fuzz / property test.

### Invariant 9 — Wasi-libc init sequence in static mode

- **Where enforced (or not):** **nowhere.** Design §5.4 spelled out
  `CallInit(impl->helpers_instance)` which "looks up `_initialize` (or
  `__wasm_call_ctors`) export, calls it once with no args. Skips
  silently if export absent." The prototype dropped this.
- **What breaks if regressed (de facto already regressed):** any
  static-mode code path that depends on C++ global constructors. cctz
  (timestamp parsing), RE2 (matches()), absl's `str_format` registry,
  and any future const-initialised global state. Today's e2e suite tests
  scalar arithmetic + string concat + const ternary only, none of which
  touches initialised globals.
- **Loud or silent?** **Silent corruption candidate** — uninitialised
  global state can return zero/empty values or trap inside the absl
  library, with backtraces that don't obviously implicate "you forgot to
  call ctors."
- **Why it passes today:** the `m28_static_link_test.cc` body explicitly
  names the gap: "Complex-message + timestamp paths are out of scope for
  this commit; their cctz dependency is covered in a follow-up." But
  there's no failing-skipped test that pins the open work — it's just
  prose. See §4 P1.

## 7. Clean implementation plan

Independent CHANGES to close out m28, ordered by dependency + risk +
value. The user explicitly invited aggressive refactoring proposals; the
ordering below prioritizes correctness gates over polish.

### CHANGE A — Pin the load-bearing strip tool invariants

- **What:** Extend `cel_runtime_stripped_wasm_bytes_test.cc` to assert:
  (1) every name in `abi::CelRuntimeHelpers()` maps to a *distinct*

## 8. Recommended sequencing

The minimum path to close m28 is **A → B → C → D → E** (tests first,
correctness fixes, then scaled validation). The rest (F–L) can interleave
once the signal-amplifier (D) is on. Specifically:

1. **A (pin strip tool invariants).** Cheap, no behavioural risk, must
   land before any future Binaryen refactor or it's a tripwire field.
2. **B (`CallInit`).** Closes the load-bearing missing-init gap. Required
   before D / K — conformance will surface cctz-init failures without it.
3. **C (rodata budget assertion).** 1 hour. Prevents the silent-corruption
   landmine before D / E exercises larger inputs.
4. **D (conformance under both modes).** The single biggest signal
   amplifier. Likely surfaces more work in the comprehension / map / list
   paths; treat surfaced failures as in-scope. Without D, "static mode
   is functional" rests entirely on the 51-cell e2e — too small a base.
5. **E (e2e matrix expansion).** Quick targeted variable-bearing cells in
   advance of D's full corpus run; E catches the most-likely regressions
   in a focused harness, D catches the long tail.
6. **F + G (`HasCelImports`, `Adopt`, `AddActiveDataSegment` unit tests).**
   Lock the new infrastructure surfaces before further refactoring (H, I)
   touches them.
7. **H (compile.cc back-half extraction).** With A–G's tests in place,
   refactor confidently. Eliminates the future-divergence risk between
   `Compile` and `CompileStatic`.
8. **I (drop dual `cel_host.*` imports).** Architectural cleanup,
   ordered after H because it touches the same `compile.cc` regions.
9. **J (`cel.abi` LinkMode field).** Independent; sequence anywhere
   after H.
10. **K (bench under both modes).** Sequence after D — conformance is
    the correctness gate, bench is the perf gate; perf claims rest on
    correctness.
11. **L (doc reconciliation).** Land in the same commit as the milestone-
    closing change, per CLAUDE.md's "Closing out a planning doc" rule.

**Net cost estimate:** A 0.5d + B 1d + C 1h + D 1d (+ surfaced work, est.
1–3d) + E 1d + F 0.5d + G 0.5d + H 1d + I 1d + J 1d + K 1.5d + L 0.5d =
~10–12 engineer-days to close, dominated by the conformance-surfaced
follow-ups in D. The minimum bar to "milestone shippable" — A, B, C, D, E,
L — is ~5–7 engineer-days.

**Rationale for ordering:** the most-expensive failures (silent
corruption in invariants 1, 6, 9) have no test signal today. Sequencing
puts those gates first; aesthetic refactors (H, I) and feature additions
(J, K) follow once the safety net is up.
