Purpose: decide whether to enable the GitHub issue tracker on the
(public) `augustinemathew/cel-wasm` repo and file these, or keep the
pin file as the tracker.  Generated by auditing all 57 `GTEST_SKIP`
sites in the first-party tree.

## Headline

**57 skips, but only ~21 are bugs.**  The other ~36 are by-design
static-subset rejections, deferred features with a recorded design
decision, or test-harness limitations.  Filing all 57 would publish
mostly noise; filing the ~21 would publish a credible, specific
defect list.

One caveat on the count: the 5 host-origin P0s found by today's

## B. NOT bugs — do not file

**By design, static subset (`RejectDyn`) — 11.**  `m5b_test` ×6 and
`wkt_field_set_test` ×2 skip because a bare `{}` or empty map
literal types as `map(dyn, dyn)` and the static subset rejects dyn
before codegen runs.  That is the documented design, not a defect.
Same for `HostFnTypeMatrix.ExplicitTypeArgNotApplicable` (the `type`
type is out of scope per `m21-host-call-adapter.md`).

**Permanently rejected per a milestone decision — 8.**
`foreign_fn_type_matrix_test` ×3 record that the celfn grammar has
no `option(...)` / `type` alternative and m24 §14 **permanently**
rejects them; `host_fn_type_matrix_test` ×4 record that there is no
celfn IDL spelling for the WKT `Any`/`Struct`/`Value`/`ListValue`
host-fn args, all auto-peeled at field read instead; plus the
optional<T> IDL row.  These are scope boundaries with a citation.

**Test-harness limitations — 8.**  `runtime/cel_list_test.cc`
(trap unobservable from gtest), `cel_runtime_wasm_test.cc` (arena
chunk outside the host-visible window), `wat_runner_test.cc` ×2
(c-api harness panics on tail-call; covered by production-engine
tests), `m9_test` ×2 (needs an AttributePattern surface in the
harness), `slot_aliasing_test.cc` ×2 (one is a template
placeholder).  Nothing to fix in the product.

**Deferred features with a recorded decision — 9.**  Component/
foreign-fn rows blocked on named blockers (`kBlockerB2`,
`kNoErrorResultVariant`), `m7_test` wrapper auto-peel (M8),
`m4_test` bound `list<string>` (host-arena gap — arguably now part
of cluster #4-#8), `wkt_field_set_test` Any-unwrap rows,
`ParserSourceCodepointLimitNotConfigurable` (cel-cpp's 100 k
codepoint cap isn't overridden — a config gap, not a miscompile).
These are roadmap items; they'd be reasonable as issues **labelled
as enhancements**, not defects.

## Recommendation

1. **If the goal is an accurate public defect list:** enable issues
   and file section A only (21 items, ~8 of them P0).  That reads as
   a project with rigorous self-knowledge — every entry has a
   reproducer, an observed-vs-expected, and a named fix layer.
2. **If the goal is to avoid publishing an unflattering P0 count on
   a public repo before the fixes land:** keep issues disabled, let
   the in-flight agent close #4-#8, then reassess.  The pin file
   already functions as the tracker, and `scripts/bug_pins.py list`
   renders the queue.
3. **Either way:** do not file section B.  Those skips are the
   system working as designed and would make the tracker
   untrustworthy.

Sequencing note: 8 of the 23 defects are P0, and 5 of those are one
in-flight fix.  Filing after that lands turns "8 open P0s" into "3
open P0s", which is a materially different first impression for a
public repo.
