# M14 Slice 0 review — CEL optionals WAT-first design lock

Date: 2026-05-21
Branch: `cel_optional` (uncommitted working tree)
Slice scope: WAT-first ABI lock for the M14 (CEL optionals) workstream.
No production C kernels, codegen, or parser wiring yet — those land in
Slice A.

## Verdict — clean, with two doc-vs-code drifts and one shadowed bug

Slice 0 stayed inside Slice 0. The four new WATs assemble cleanly, the
no-op stub registration mirrors the M7B pattern faithfully, the four
smoke tests are structurally correct, and the wat-traces.md walkthroughs
honestly explain the layout trade-offs. The two open §3 questions Slice
0 was meant to resolve (OptionalCell layout, select-field kernel
sharing) are now decided and the rationale is written down where Slice
A will look for it. There is no architectural drift to flag — there is
no prior M14 build to drift from, and the layout choices are consistent
across all four WATs.

The top three items the reviewer should look at first:

  1. **wat-traces.md falsely claims the smoke tests run against
     "functional C++ stubs that implement the kernel semantics."**
     They do not. `RegisterPendingM14Imports` binds pure no-op
     trampolines (`NoopCelHostThreeArg`) just like
     `RegisterPendingM7BImports`. The four tests only verify
     instantiation + `$eval` return-value (the workspace slot offset),
     they cannot verify the post-eval CelValue contents because the
     stubs never write anything. This is misleading documentation, not
     a bug — but it inflates the apparent test coverage. **P1 doc fix.**

  2. **The four `WatRunnerM14Test` tests fail today.** Not Slice 0's
     fault — they're blocked by the same pre-existing
     `wasi_snapshot_preview1::environ_get` regression that breaks
     every other test in `wat_runner_test.cc` (confirmed by running
     `WatRunnerTest.LiteralFortyTwoReturnsCelIntFortyTwo` on the same
     branch: 6 failures with identical 16-byte error trailer pattern).
     Slice 0 inherits the regression but does not address it. Flag for
     the reviewer because shipping Slice 0 with 4 visibly-failing tests
     in the suite normalises a broken signal. See "Pre-existing issues"
     below.

  3. **WAT 3 (`m14_optional_select_field.wat`) does not actually
     exercise the OptionalCell layout end-to-end** because the kernels
     are no-ops — but the *header documentation* is doing the
     load-bearing work of locking the kernel ABI. The reviewer should
     read the four WAT headers as the spec, not the executable traces.
     This is fine for Slice 0's purpose, but it means Slice A MUST
     re-run these WATs against real kernels and re-verify byte-exact
     memory layouts before the lock holds.

Overall: ship-worthy as a Slice 0 design lock. The doc drift in
wat-traces.md (item 1) should be corrected in a follow-up edit before
Slice A starts.

## 1. Coverage of §3 design questions

The design doc (`m14-optionals.md` §3) listed four open questions that
Slice 0 was meant to resolve.

### §3.1 — OptionalCell payload representation

**Resolved. Verdict locked in writing.**

`m14_optional_of_int.wat` (lines 8-37) freezes the 32-byte layout:

```
struct OptionalCell {
  uint32_t present;        // offset  0
  uint32_t _pad;           // offset  4
  CelValue inner;          // offset  8, 24 bytes
};
```

Both rejected alternatives are addressed in writing with reasoning
that survives scrutiny:

  - **Tag-encoded NONE/SOME** (rejected): the WAT 1 header argues that
    splitting `CEL_OPTIONAL` into `CEL_OPTIONAL_SOME=15` /
    `CEL_OPTIONAL_NONE=16` would double the polymorphic-switch surface
    in `cel_equals_at_vv`, `cel_log`, `type()` lookup, future codegen
    dispatch, etc. The wat-traces.md M14.1 walkthrough quantifies it
    as "two arms × ~12 switches = 24 extra edges in a sprawl pattern."
    Honest framing.
  - **Shared-static None sentinel** (rejected for now, kept as
    post-Slice-D optimisation): the WAT 1 header explicitly calls out
    that the ABI doesn't change if a future perf pass layers in a
    shared sentinel — the constraint is purely on kernel writers
    ("must not write through opt_slot if it might point at the
    sentinel"). Defer-with-clear-trigger is the right call.

Offsets are consistent across the 4 WATs: every reference to
`cell.present` is at offset 0, `cell._pad` at offset 4, `cell.inner`
at offsets 8-32, the cell itself is 32 bytes. No skew.

### §3.2 — Single-kernel `cel_optional_select_field_at_vv` for both `.?field` and Select-on-optional

**Resolved. The most load-bearing decision in Slice 0.**

`m14_optional_select_field.wat` (lines 1-91) and the wat-traces.md
M14.3 walkthrough explicitly commit: both AST shapes (Call("_?._",
[obj, key]) AND kSelectExpr with optional-typed operand) route through
one runtime export. The kernel polymorphic-dispatches on `src.kind`:
`CEL_OPTIONAL` unwraps then falls through to the inner-kind branch;
`CEL_MAP_ARENA` / `CEL_MAP_HOST` / `CEL_MESSAGE` do the direct lookup.

The argument for one kernel (WAT 3 header lines 64-74; wat-traces.md
M14.3 "Why one kernel and not two"):
  - The absent-key → optional.none() semantic is identical for both
    AST shapes; the only differential is path (2)'s outer present-flag
    check.
  - LowerSelect's new branch is 4 lines instead of needing a sibling
    kernel.
  - One ABI, one cel-cpp parity surface, one runtime export.

This aligns with probe Q11 (`ast_shape_probe_test.cc:432`) which
asserts the checker leaves Select-on-optional as `kSelectExpr` with
the result type promoted — verbatim what the WAT header claims.

### §3.3 — `type()` for CEL_OPTIONAL

**Not addressed by Slice 0** — but design doc §3.3 (m14-optionals.md
lines 254-264) already considered this resolved at design time:
`cel_type.c:39` gets `"optional_type"` filled in. Slice 0 didn't need
a WAT for this. Acceptable scope discipline.

### §3.4 — `ofNonZeroValue` per-kind zero predicate

**Not addressed by Slice 0** — design doc §3.4 calls it "~40 LOC of
pure C", no ABI surface to lock. Acceptable to defer to Slice A.

### Things §3 did not list that Slice 0 surfaced anyway

  - **`orValue` unwrap semantics.** WAT 4 / wat-traces.md M14.4 makes
    explicit that `optional.none().orValue(default)` returns the bare
    inner type (not another optional). Worth promoting to the design
    doc since `or` and `orValue` have the same 3-arg ABI but differ in
    the present-branch's output kind.
  - **`or` vs `orValue` ABI symmetry.** WAT 4 wat-traces footer
    (M14.4 last paragraph) declines to ship a separate WAT for `or`
    on the argument that its kernel signature matches `orValue`'s 3-arg
    shape — only the present-branch's memcpy destination kind differs.
    Reasonable; Slice A can validate.

## 5. Doc-vs-code drift

### 5.1 wat-traces.md claims functional stubs; reality is no-op stubs

This is the biggest drift in the slice. wat-traces.md M14 overview
(line ~1696) states:

> All four assemble cleanly via `wasm-as`. End-to-end execution
> through `wat_runner` is wired in `wat_runner_test.cc` against
> functional stubs that implement the kernel semantics in C++ —
> when the production C kernels land in Slice A, the stubs go away

And M14.1 (line ~1751):

> **Runnable today** — the kernel doesn't exist in
> `cel_runtime.wasm` yet; `wat_runner_test.cc` registers a
> functional C++ stub on the `cel` linker module that implements
> the contract above. The stub goes away when Slice A lands the
> real C kernel; the assertions stay.

Reality: `RegisterPendingM14Imports` binds `NoopCelHostThreeArg` (a
literal `return nullptr;` trampoline that takes no arguments and
writes nothing). The wat_runner_test.cc M14 tests (lines 985-1031)

compile-time constant from the WAT's `(i32.const 40)`-style return).

CelValue contents.

The test comments (lines 974-983) DO correctly state "They do NOT
assert on the post-eval CelValue contents — the stubs are no-ops so
the out_slots stay zero. Byte-exact semantic verification lands in
Slice A". So the TEST file is honest; wat-traces.md is the one with
the false claim.

**Severity:** P1. The misclaim doesn't affect correctness, but it
overstates Slice 0's coverage. Fix in wat-traces.md: change "functional
stubs that implement the kernel semantics" to "no-op trampolines (no
side-effect on linear memory); end-to-end semantic verification of

## 6. Coverage gaps

### 6.1 Smoke-test coverage

Every WAT has a corresponding `WatRunnerM14Test` smoke test (4 WATs ↔
4 tests). Coverage is uniform.

Each test:
  - Loads the WAT via `LoadWat`.
  - Calls `RunWat(in)` (which does parse-WAT → assemble → instantiate
    → call `$eval`).
  - Asserts `out` is OK.
  - Asserts `out->eval_return` equals the WAT's literal return slot
    offset.

This is the bare minimum for a Slice 0 smoke test. It verifies:
  - The WAT assembles.
  - All imports resolve under the linker (i.e. import names + arities
    match what `RegisterPendingM14Imports` binds).
  - `$eval` runs to completion without trapping.
  - `$eval` returns the literal-constant slot offset the WAT promises.

What it does NOT verify (intentionally, per the test header comment):
  - The post-eval CelValue at the returned slot. (Stubs are no-ops.)
  - The OptionalCell allocated in the arena. (Stubs don't allocate.)
  - The `cell.present` flag, `cell.inner`, layout offsets. (Stubs
    don't write.)

This is fine for Slice 0 as a "WAT-link smoke test", but reviewers
should treat the test names ("...Instantiates") as accurate: they
test instantiation, not semantics.

### 6.2 ABI surfaces not yet WAT-locked

Slice A will ship 8 production kernels (per m14-optionals.md §4-A).
Slice 0 locks 4 of them in WAT. The other 4:
  - `cel_optional_none_at_v` (or whatever shape — 1-arg out_slot?)
  - `cel_optional_value_at_v` (extract inner; error on None)
  - `cel_optional_or_at_vv` (preserves optional-ness)
  - `cel_optional_ofNonZeroValue_at_v` (per-kind zero predicate)

The first three are claimed by wat-traces.md M14 prose to "ride the
WAT 1 / WAT 2 / WAT 4 ABI" by symmetry. That's a reasonable claim for
1-arg and 3-arg shapes, but `ofNonZeroValue` has per-kind branch logic
(§3.4) that Slice 0 doesn't trace at all. Slice A should add at least
one WAT exercising `ofNonZeroValue(0)` → None and `ofNonZeroValue(7)`
→ Some.

The index kernels (`map_optindex_*`, `list_optindex_*`,
`optional_list_optindex_*`, etc — 5+ overloads per m14-optionals.md
§1.8) are Slice B scope; Slice 0 doesn't owe them coverage.

### 6.3 Equality semantics (§3.2 of design doc)

Design doc §3.2 calls out a new `cel_equals_at_vv` arm for
CEL_OPTIONAL. Slice 0 doesn't WAT-trace this. The arm is internal
codegen plumbing — not a new exported kernel — so arguably doesn't
need its own WAT. But Slice A's first conformance run will hit
optional-vs-optional equality and `cel_equals` will fall through to
the existing `default: false` ladder, producing wrong-but-not-crash
behaviour. Worth surfacing in the Slice A plan as a "must add before
running conformance" tick-box.
